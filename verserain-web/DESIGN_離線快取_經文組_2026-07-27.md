# 離線快取 — 打過的經文組 + 全部主題經文組(Design Doc)

**Author:** Drafted for David · **Date:** 2026-07-27 · **Status:** Proposal for review

> 目標:飛機上、地鐵裡、偏鄉沒訊號時,VerseRain 照樣打得開、照樣能打經文雨。
> **凡是打過的經文組自動離線可用;主題經文組(主題:讚美 / 禱告 / 盟約…)全部預先快取。**

---

## 1. 一句話

加一層 **Service Worker(app shell)+ IndexedDB(經文資料與素材)**,
把「打得開 App」和「有經文可打」這兩件事從網路上拆下來。
使用者不必按任何按鈕 —— **打過就快取**,主題經文組則在第一次上線開 App 時整批鏡像。

---

## 2. 現況盤點(先講壞消息)

我把整條路徑量過一遍。**今天 VerseRain 完全離線 = 白畫面**,跟資料快不快取無關:

| 層 | 現況 | 離線 |
|---|---|---|
| **App shell** | [`public/sw.js`](public/sw.js) 只有 `push` / `notificationclick` **兩個 handler,沒有 `fetch` handler、沒有 precache** | ❌ 白畫面 |
| 內建經文(各語言) | 打包成 JS chunk,`import()` 動態載入([`src/verseLoader.js`](src/verseLoader.js))。`index` chunk 2.4 MB,語言 chunk 60 KB–652 KB | ❌ chunk 抓不到 |
| **主題經文組** | **沒有打包進 bundle**,開機時向 PartyKit `/custom-sets` 抓([App.jsx:5608](src/App.jsx:5608))。失敗只 `console.error`,state 留在 `[]` | ❌ 整批消失 |
| 我自己的題庫 | 已鏡像在 `localStorage.verseRain_custom_sets` | ✅ |
| 花園 / 進度 | `localStorage.verseRain_gardenData` + [`gardenSync.js`](src/lib/gardenSync.js) 單調遞增合併 | ✅ 離線照記,回線再合 |
| 排行榜寫入 | `/api/submit-score`、`/api/submit-verse-stat` 都是 `.catch(() => {})` 射後不理 | ⚠️ 靜靜地掉 |
| 題庫素材 | preset 背景 SVG(全部 48 KB)、影片背景(2.7 MB)、`bgm.mp3` **9.4 MB**、自訂背景/音樂與親聲錄音走 PartyKit 分塊 base64 | ❌ |
| 語音朗讀 | `speechSynthesis`(系統語音) | ✅ 多數裝置可離線 |
| 雙語第二語言 | bolls.life / `/api/*`,快取在 `localStorage.verserain_bible_cache` | ⚠️ 只有看過的那節 |

## 3. 「能離線打一組經文」到底需要什麼

打開一組經文組會用到六樣東西,缺一不可:

1. **App shell** — `index.html` + 主 JS/CSS chunk(Phase 1)
2. **語言 chunk** — 該題庫語言的 `verses_*.js`(Phase 1 runtime cache)
3. **題庫本體** — 內建的在 chunk 裡;主題/發佈題庫要靠 IndexedDB 鏡像(Phase 2)
4. **素材** — 背景圖/影片、BGM、自訂背景音樂、親聲錄音(Phase 2)
5. **雙語第二語言經文**(若使用者開了雙語)(Phase 2)
6. **寫入端要能失敗而不壞掉** — 分數、統計、花園(Phase 3)

## 4. 架構:三層快取

```
┌─ Service Worker (Workbox) ─────────────────────────────┐
│  precache:  index.html · index.js/css · icons          │
│             rain.mp3 · set-backgrounds/*.svg   ≈2.8 MB │
│  runtime :  verses_*.js (CacheFirst, 用到才存)          │
│             fonts.gstatic.com (CacheFirst, 1 年)        │
│             backgrounds/*.mp4 (CacheFirst, LRU)         │
│  navigate:  fallback → 快取的 index.html                │
└────────────────────────────────────────────────────────┘
┌─ IndexedDB  (src/lib/offlineSets.js) ──────────────────┐
│  store: publishedSets  — /custom-sets 整包鏡像 (SWR)     │
│  store: playedSets     — 打過的題庫 + playedAt (LRU)     │
│  store: assets         — 自訂背景/音樂/親聲 Blob         │
│  store: outbox         — 離線時的分數/統計待送佇列        │
└────────────────────────────────────────────────────────┘
┌─ localStorage(維持現狀,不動) ──────────────────────────┐
│  verseRain_custom_sets · verseRain_gardenData           │
│  verserain_bible_cache(雙語第二語言)                    │
└────────────────────────────────────────────────────────┘
```

**為什麼經文資料放 IndexedDB 不放 localStorage:** 光是 `/custom-sets` 鏡像就 1.5 MB,
localStorage 配額約 5 MB,而現有 key(花園、題庫、聖經快取、統計)已經吃掉一大塊。
[App.jsx:5079](src/App.jsx:5079) 那句 `catch { /* storage full */ }` 就是配額已經在邊緣的證據。

## 5. Phase 1 — App shell 離線(地基)

導入 **`vite-plugin-pwa` 的 `injectManifest` 模式**。選 `injectManifest` 而不是 `generateSW`,
是因為現有 `public/sw.js` 的推播 handler **必須原封不動保留** —— 每日經文推播(Web Push + APNs)
整條線都靠它([SETUP_每日經文推播_APNs_2026-07-09.md](SETUP_每日經文推播_APNs_2026-07-09.md))。
`injectManifest` 只是把 precache 清單注入我們自己的 SW,推播邏輯照舊。

> 相容性已確認:本專案 `vite@8.0.5`,`vite-plugin-pwa@1.3.0` 的 peer 是
> `vite: ^3 || ^4 || ^5 || ^6 || ^7 || ^8` ✓
> (備案:若日後版本卡住,自寫一個 ~40 行的 Vite plugin 在 `closeBundle` 時
> 產生 precache 清單也可以,但目前沒必要。)

### 檔案變更

| 檔案 | 變更 |
|---|---|
| `vite.config.js` | +`VitePWA({ strategies: 'injectManifest', srcDir: 'public', filename: 'sw.js', registerType: 'autoUpdate' })`;`injectManifest.globPatterns` 指定 precache 範圍 |
| `public/sw.js` | 頂部加 `precacheAndRoute(self.__WB_MANIFEST)` + runtime route;**push / notificationclick 兩段完全不動** |
| `src/App.jsx` | 現有 `navigator.serviceWorker.register('/sw.js')`([App.jsx:4593](src/App.jsx:4593))雖然在 mount 的 `useEffect` 裡跑,但**整個 effect 被 `isWebPushSupported()` 擋住**([App.jsx:4581](src/App.jsx:4581))—— 註冊要與推播支援度解耦 |
| `src/main.jsx` | 建議改在這裡註冊(更早、與推播無關),推播流程改用 `navigator.serviceWorker.ready` 取得 registration |

> ⚠️ **覆蓋率陷阱:** 註冊時機本身沒問題(mount 就跑),問題在**閘門**——
> `isWebPushSupported()` 要求 `serviceWorker` + `PushManager` + `Notification` 三者齊備
> ([`pushConfig.js:20`](src/pushConfig.js:20))。以下族群**有 Service Worker 但沒有 PushManager**,
> 今天完全拿不到 SW,離線也就到不了他們身上:
>
> | 族群 | SW | PushManager | 今天有 SW 嗎 |
> |---|---|---|---|
> | iOS Safari 一般分頁(還沒「加到主畫面」) | ✅ | ❌(iOS 只在 standalone 給) | ❌ |
> | LINE / FB / WeChat 站內瀏覽器 | ✅ | ❌ 多數沒有 | ❌ |
> | iOS App Store 原生版 | ❌ | ❌ | ❌(WKWebView 本來就沒有,見決策 A) |
> | Android Chrome / TWA / 桌面 / iOS PWA | ✅ | ✅ | ✅ |
>
> **這對 VerseRain 特別要命** —— 雲端家人的每日分享連結是從 **LINE 群組**點進來的,
> 那條流量正好落在拿不到 SW 的那一格。Phase 1 必須把註冊搬出這個閘門,
> 否則離線功能只涵蓋已經「加到主畫面」的使用者。

### 更新策略

`registerType: 'autoUpdate'` + 一個「新版本已就緒,點擊更新」toast。
沒有這個 toast,precache 會把使用者釘在舊版本上 —— 這是 PWA 最常見的翻車點。

### 驗收

飛航模式開 App → 首頁正常 → 選一組**內建**經文組 → 打得完一輪。

## 6. Phase 2 — 經文資料快取(本案主體)

新檔 **`src/lib/offlineSets.js`**,純函式 + IndexedDB,比照 [`gardenSync.js`](src/lib/gardenSync.js)
的作法(可測試、邏輯與 React 分離),並附 `offlineSets.test.mjs`。

```js
// src/lib/offlineSets.js — 對外 API 草案
export async function readPublishedSets()            // → 陣列(離線第一手來源)
export async function writePublishedSets(sets)       // ← /custom-sets 抓成功後覆寫
export async function cachePlayedSet(set, opts)      // 打過就存 + 暖素材
export async function listPlayedSets()               // → [{ id, playedAt, bytes }]
export async function isSetCached(setId)             // → 給「已離線可用」標章用
export async function evictLRU(targetBytes)          // 超出配額時汰舊
export async function clearOfflineData()             // 設定頁「清除離線資料」
```

### 6.1 主題經文組 —— 整包鏡像 + SWR

改 [App.jsx:5608](src/App.jsx:5608) 那個 `useEffect`:

```js
// 之前:fetch → setPublishedVerseSets(data)   ← 離線就是空的
// 之後:
readPublishedSets().then(cached => { if (cached?.length) setPublishedVerseSets(cached); });  // 先上畫面
fetch(HOST + '/custom-sets')
  .then(r => r.json())
  .then(data => { if (Array.isArray(data)) { setPublishedVerseSets(data); writePublishedSets(data); } })
  .catch(() => { /* 離線 — 已經用快取渲染過了 */ });
```

**一次改動,146 組主題經文組全部離線可用**(連同其餘 158 組已發佈題庫)。
既有的 `publishedVerseSets` × `customVerseSets` 合併邏輯([App.jsx:5643–5677](src/App.jsx:5643))
完全不用動 —— 它只認 state,不管資料哪來的。

**要整包還是只存主題組?** 建議**整包**:gzip 695 KB、IndexedDB 1.5 MB,便宜;
而且順手把線上冷啟動的 2.2 MB 阻塞變成背景 revalidate。
(只濾 `TOPIC_PREFIX_REGEX`([App.jsx:3695](src/App.jsx:3695))+ 當前語言的話約 50 KB,但省不到哪去,還會讓「打過的別人題庫」離線消失。)

### 6.2 打過就快取

**掛鉤點:** `selectedSetId` 已經有一個 `useEffect`([App.jsx:4394](src/App.jsx:4394)),
但更準確的語意是「真的開打」而不是「點進去看」。建議掛在:

- `startGame()`([App.jsx:7915](src/App.jsx:7915)) —— 一般開打路徑
- `launchSetById()`([App.jsx:6442](src/App.jsx:6442)) —— 深連結 `?startSet=` 與雲端家人「開始挑戰」

兩處都呼叫同一個 fire-and-forget:

```js
cachePlayedSet(currentSet, { version, bilingualSecondaryVersion }).catch(() => {});
```

`cachePlayedSet` 做四件事:

1. 寫入 `playedSets`(題庫全文 + `playedAt`)
2. **暖語言 chunk** —— `await loadLanguageSets(set.language)`,確保該 `verses_*.js` 落進 SW runtime cache
3. **暖素材**(見 6.3)
4. **暖雙語第二語言**(見 6.4)

> 注意:內建題庫的經文本來就在語言 chunk 裡,`playedSets` 對它們其實只是記錄 `playedAt`;
> 真正靠這份記錄活下來的是「別人發佈、我打過」的題庫 —— 它們不在 bundle 也不在我的 `custom_sets`。

### 6.3 素材

| 素材 | 來源 | 快取方式 |
|---|---|---|
| preset 背景 SVG | `/set-backgrounds/*.svg`(48 KB) | Phase 1 precache 全收 |
| 影片背景 | `/backgrounds/*.mp4`(2.7 MB) | SW runtime CacheFirst,用到才存 |
| `rain.mp3` | 116 KB | Phase 1 precache |
| `bgm.mp3` | **9.4 MB** | **見下方決策 B** |
| 自訂背景/音樂 | PartyKit `/sets/asset` 分塊 base64([`setVoiceApi.js`](src/setVoiceApi.js)) | `cachePlayedSet` 抓下來存 IndexedDB `assets`,key = `setId\|assetId` |
| 親聲錄音 | PartyKit `/sets/verse-voices` + `/sets/voice` | 同上 |

`getSetAssetDataUrl()`([setVoiceApi.js:53](src/setVoiceApi.js:53))現在是 in-memory `Map`,
改成 **IndexedDB 優先 → 網路 → 回寫**,呼叫端一行都不用改。

### 6.4 雙語第二語言

`cachePlayedSet` 時把該題庫每節的第二語言經文預先解析進現有的
`verserain_bible_cache`(`getCachedBibleVerse` / `setCachedBibleVerse`,[App.jsx:1133–1155](src/App.jsx:1133))。
沿用現有 key 格式,雙語模式離線就會自然命中。

> 注意配額:一組 15 節 × 約 200 字 ≈ 6 KB,可接受;但這是塞進 **localStorage** 的,
> 若 Phase 4 量測顯示壓力大,再把 `verserain_bible_cache` 整個搬到 IndexedDB(獨立小 PR)。

## 7. Phase 3 — 離線時的行為要對

### 7.1 寫入佇列(outbox)

今天離線打完一輪,分數是**靜靜掉的** —— 三個端點都 `.catch(() => {})`:

- `/api/submit-score`([App.jsx:8184](src/App.jsx:8184)、[8266](src/App.jsx:8266)、[8325](src/App.jsx:8325)、[20947](src/App.jsx:20947))
- `/api/submit-set-score`([App.jsx:8368](src/App.jsx:8368))
- `/api/submit-verse-stat`([App.jsx:5582](src/App.jsx:5582)、[5592](src/App.jsx:5592))

作法:包一層 `postWithOutbox(url, body)` —— 失敗就把 payload 寫進 IndexedDB `outbox`,
監聽 `window.online` 時重送。每筆帶 **client-generated `eventId`**,
server 端以 `eventId` 去重,避免重送把分數灌兩次。

> **花園不用動。** [`mergeGardens()`](src/lib/gardenSync.js) 是單調遞增的欄位級合併,
> 離線期間寫 localStorage、回線再合,本來就正確 —— 這是先前
> [FIX_数据丢失与两端不一致_2026-06-16.md](FIX_数据丢失与两端不一致_2026-06-16.md) 打下的底子。

### 7.2 UI

| 位置 | 變更 |
|---|---|
| 離線橫幅([App.jsx:21911](src/App.jsx:21911)) | 已存在,維持 |
| 題庫列表 | 已快取的題庫加 **「已離線可用」** 小標章(`isSetCached`) |
| 離線時停用 | 發佈題庫、複製題庫、雲端家人、排行榜、世界地圖、QR 掃描 —— 改為 disabled + 提示,而不是點下去靜靜失敗 |

## 8. Phase 4 — 配額與汰換

- 上限抓 **~60 MB**;用 `navigator.storage.estimate()` 量、`navigator.storage.persist()` 申請常駐
  (Chrome / Android 有效,可防系統自動清掉)。
- `playedSets` 依 `playedAt` **LRU** 汰換;主題組鏡像與 app shell **釘住不汰**。
- 汰換只丟素材與題庫全文,**不碰花園與 outbox**。

## 9. 兩個要你拍板的決策

### 決策 A — iOS App Store 版拿不到 Phase 1

[`ios-vercel-wrapper/VerseRain/WebView.swift`](ios-vercel-wrapper/VerseRain/WebView.swift) 是一個
指向 `https://www.verserain.com/` 的**純 WKWebView**,[`Info.plist`](ios-vercel-wrapper/VerseRain/Info.plist)
裡**沒有 `WKAppBoundDomains`**。WKWebView 只有在 app-bound domain 下才跑 Service Worker;
而一旦開啟 app-bound domains,導航就被限制在自家網域 ——
**Google / Apple 登入會跳 `accounts.google.com`、`appleid.apple.com`,會被擋掉。**

| 平台 | Phase 1(shell) | Phase 2–4(資料) |
|---|---|---|
| Safari「加到主畫面」PWA | ✅ | ✅ |
| Android TWA / Chrome | ✅ | ✅ |
| 桌面瀏覽器 | ✅ | ✅ |
| **iOS App Store 原生版** | ❌ 需 app-bound domains(會撞 OAuth) | ✅ IndexedDB 在 WKWebView 正常 |

**選項:**
1. **(建議)** 先接受 iOS 原生版維持連線才能開,離線功能主打 PWA / Android / 桌面。iOS 使用者要離線就引導「加到主畫面」。
2. iOS 原生版改把 app shell **打包進 App**(本地 `index.html` + `WKURLSchemeHandler`),資料層仍走線上 —— 工程量不小,等於維護第二套發佈流程。
3. 開 `WKAppBoundDomains`,OAuth 改走 `ASWebAuthenticationSession` 原生流程 —— 可行但要動登入,風險最高。

### 決策 B — `bgm.mp3` 9.4 MB 怎麼辦

1. **(建議)** 轉一份 ~1 MB 的 64 kbps 離線版(`bgm-lite.mp3`),離線時播它。
2. 整份 9.4 MB 進 precache —— 太肥,且 Safari 對快取音檔的 range request 處理很雞掰,容易播不出來。
3. 離線就沒背景音樂,只留 `rain.mp3` 音效。

## 11. 測試計畫

**每個 PR 都要過的:**
1. DevTools → Network **Offline** + Application → Service Workers(確認 activated、precache 清單正確)
2. Application → Storage → IndexedDB 看資料真的寫進去
3. `npm run lint`、`npm run check:i18n`、`node --test src/lib/offlineSets.test.mjs`

**上線前的真機驗收(照使用者實際情境):**

| 情境 | 預期 |
|---|---|
| 線上開一次 App → 飛航模式 → 重開 | 首頁正常,主題經文組全在 |
| 線上打過「主題:讚美」→ 飛航模式 → 再打 | 經文、背景、音樂、親聲全部正常 |

## 12. 風險

| 風險 | 緩解 |
