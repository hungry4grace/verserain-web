## 一、用户报告的现象

1. **更新丢失**：今天打开「今日妥拉」/园子，状态回退到了上周，昨天一整天的更新不见了。
2. **网页与手机 App 不匹配**：
   - 果子数量不同（主要差在「推荐记录」相关的果子）。
   - 页数、时间、内容在两端不同步。

---

## 二、根因分析

经文雨的进度数据分散在三处存储，问题就出在它们之间的同步逻辑：

| 数据 | 存储位置 | 同步方式 |
|---|---|---|
| 园子 / 果子 / 连续天数 (`gardenData`) | 浏览器 `localStorage` **+** PartyKit 云端 (`garden:<playerName>`) | 登录时双向合并 |
| 推荐果子 / 作者果子 (`creatorPoints`) | Vercel KV (Redis)，按 `playerName` 和 `personalCode` 分键存 | 登录时拉取 |
| 排行榜 / 挑战次数 | Vercel KV (Redis) | 实时写入 |

页面显示的「总果子」= **本地园子果子 + 云端推荐/作者果子**（`App.jsx`：`totalFruits = localFruits + creatorPoints`）。两个来源、两套同步机制，正是所有问题的根。

### 根因 1：登录同步会用「本地旧快照」覆盖云端（→ 回退到上周）

`App.jsx` 登录时的合并逻辑原本是：读本地 → 拉云端 → 合并 → 写回云端。其中有两条会导致「整包覆盖云端」的路径：

- **网络错误**（`.catch`）：直接拿本地数据 push 回云端。
- **HTTP 非 200**（如 404 / 500 / 限流）：`r => r.ok ? r.json() : null` 会让 `data = null` → `remoteGd = {}`（空）→ 合并后只剩本地数据 → 又 push 回云端。这条**更常见**。

只要某次登录时云端读取没成功，App 就用了当前设备上较旧的本地副本，并**整包覆盖**掉云端较新的版本——这完美解释了「不是丢一天，而是整体回退到上周某个快照」。

### 根因 2：`personalCode` 每台设备各自随机生成（→ 两端果子不一致）

`personalCode`（个人码 / 邀请码）此前**只存在各设备的 `localStorage`**，取不到就新生成一个，从未与账号绑定。所以网页和手机几乎一定是两个不同的码。而推荐果子有一部分按 `personalCode` 这个键存（`submit-referral-point` 的 `author: personalCode || currentPlayerName`），读取时也按当前设备的码去取 → **两端读到不同的推荐果子 → 总果子不同**。

### 根因 3：服务端 `save-garden` 直接覆盖、无任何合并或备份

PartyKit 的 `save-garden` 原本只有一行 `storage.put(garden:<playerName>, gardenData)`，**没有备份、没有历史版本、没有字段合并**。因此根因 1 一旦触发，旧数据立刻覆盖新数据且无法找回。

## 三、改动内容

### A. `src/App.jsx`

**A1. 登录同步逻辑重写（核心修复）** — 杜绝「用本地覆盖云端」

把云端读取结果明确分成三种情况：

- **200 且有数据** → 字段级合并后写回云端（安全）。
- **404（新玩家无云端数据）** → 写回本地（安全）。
- **其他任何异常（非 200 / 网络错误）** → 视为「云端状态未知」，**只用本地显示，绝不写回云端**。

并且连续天数 `_activity` 改为**两边并集、按天取较大值**，不再丢任何一天。

**A2. 个人码登录后统一**

- `personalCode` 由只读改为可写状态，新增 `adoptAccountPersonalCode()`：登录拿到账号的统一个人码后，若与本地不同，先把旧码记入 `verserain_prev_personal_codes`，再覆盖本地码。
- 在邮箱登录、LINE 登录两处成功回调里调用它；并在 register / login / verify-email 请求中带上本地码供服务端首次绑定。

**A3. 果子读取兼容历史旧码** — 历史果子不丢

果子读取改为查询 `playerName + 当前个人码 + 所有历史旧码`，去重后相加。这样统一个人码之后，旧码下累积的推荐果子仍被计入。

### B. `src/party/server.js`

**B1. `save-garden` 改为服务端防御性合并（最关键的兜底）**

存储前先读出已有数据，**逐节经文取较高的 `stage` / `fruits`，活动天数取并集**。存储**只增不减**——即使将来任何客户端再 push 一份残缺/过时数据，也无法降低已有进度。这是防止「单次错误写入造成数据丢失」的最后一道防线。

**B2. 账号绑定个人码**

`register` / `verify-email` / `login` 三个端点：账号若还没有 `personalCode`，用客户端这次带上来的码**首次绑定**并存入 user；之后所有端点都在返回的 user 里带上 `personalCode`，保证所有设备登录同一账号复用同一个码。

## 四、风险与兼容性

- **A1 / B1（同步与合并）**：纯防御性，只会让数据更安全、不改变任何正常语义。低风险。
- **A2 / A3 / B2（个人码统一）**：
  - 第一个登录的设备「捐出」自己的本地码作为账号的统一码，其余设备登录后跟随。
  - 旧码下的历史果子通过 A3 的多键查询保留，不会消失。
  - `personalCode` 同时是邀请码：统一后，分享链接/二维码里的邀请码会变成账号的统一码（同一账号在不同设备会一致，属于预期改善）。
  - 中等风险，建议部署后用一个测试账号在两台设备上验证（见第六节）。

## 六、部署后验证清单

1. **不再覆盖**：A 设备做几个新进度并确认已同步云端；B 设备（数据较旧）登录同一账号——B 不应抹掉 A 的新进度，双方应合并到较高值。
2. **断网兜底**：登录瞬间断网或让云端返回非 200，确认 App 仅用本地显示、**没有**把本地写回云端（控制台会打印 `[garden-sync] ... without pushing to server`）。
3. **果子一致**：同一账号在网页与手机分别登录，确认「总果子 / 推荐果子」两端一致。
4. **历史果子未丢**：统一个人码后，确认推荐果子总数没有变少（旧码下的果子仍计入）。
5. **连续天数**：跨设备登录后，连续天数不应回退或丢天。

## 七、关于昨天已丢失的数据

PartyKit 服务端**没有备份/历史版本**，云端那份昨天的进度已无法从代码层面找回。唯一现实的机会：**昨天用网页更新的那台电脑、那个浏览器**，只要之后没登出、没清缓存、没重新登录，其 `localStorage` 里可能仍存着昨天的完整数据。提取方法（在该浏览器 Console 执行）：

```js
copy(localStorage.getItem('verseRain_gardenData'))
```

提取后核对其中 `_activity` 是否包含昨天的日期，再在**已部署 B1 合并防线之后**重新登录，让它安全地合并回云端（合并只增不减，不会再被覆盖）。
